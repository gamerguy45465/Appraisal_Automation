# Security review

This implementation was reviewed against the [OWASP Top 10:2025](https://top10.owasp.org/2025/) with emphasis on mortgage documents and authenticated browser automation. It supports local Windows development and a single-user Azure website using an Azure Playwright workspace browser. Companion pairing and its backend have been removed. This is a scoped code review, not a penetration test or certification. Controls below describe the intended application boundaries and must be preserved during maintenance. See [Azure browser configuration and acceptance](azure-browser.md).

| OWASP category | Application treatment |
| --- | --- |
| A01 Broken Access Control | Local mode binds to loopback. Hosted mode uses an exact configured HTTPS Host/Origin and authenticated workspace sessions. Cloud browser frames and input require the owning session and current job, with CSRF and exact Origin checks for writes. Human input is unavailable during automated preparation. Automation resumes only after a confirmed authenticated R3 URL, and model tools validate the order-page destination before observing or filling fields. |
| A02 Security Misconfiguration | Use restrictive security headers, local assets, no public CORS and no public debug response stacks. Hosted configuration fails closed without an exact HTTPS origin and workspace access key; require Azure HTTPS Only and one instance/process. Disable inherited external tracing for mortgage data. |
| A03 Software Supply Chain Failures | Install dependencies with npm, retain the lockfile, use reproducible installation, and review dependency audit findings. Recheck changed dependencies instead of assuming a prior clean audit remains current. |
| A04 Cryptographic Failures | Provider and R3 connections use HTTPS with certificate verification, explicit selected keys and pinned endpoints. Hosted viewer traffic uses HTTPS. Azure browser connections use a validated secure WebSocket endpoint and explicit managed identity tokens. Local form traffic stays on loopback. Workspace authentication uses a random access code and constant-time digest comparison. Keys remain in application memory; hosted R3 login input also transits App Service and the remote browser, outside model context. |
| A05 Injection | Validate inputs and PDF signatures; pass secrets as data to fixed PowerShell code; render status text without HTML interpolation. Treat uploaded documents and page content as untrusted data. Do not expose arbitrary JavaScript, shell execution, or submission tools to the agent. |
| A06 Insecure Design | Deterministic VA/FHA/purchase rules precede browser work. Tool restrictions enforce human-only order submission; prompt text is not the only control. One active job and bounded model/tool execution limit concurrent cost and state confusion. |
| A07 Authentication Failures | Hosted workspace sign-in requires a separately configured random access code and produces a secure HTTP-only SameSite cookie. The user completes R3 sign-in and CAPTCHA in the local browser or authenticated cloud viewer. The order form has no R3 credential fields, environment operations or model login tools. Transient human viewer input is separate from agent observations and mutations, which remain unavailable until authenticated order-page preparation begins. |
| A08 Software or Data Integrity Failures | Validate model output against a structured schema and business rules. Check the exact R3 create-order URL; fill only the immutable approved plan. Appraisal recommendations use cited source facts, inspected program-matching products, and a mandatory property/lender-requirements review warning without changing uncertain property facts. Restrict runtime reads to inspected page/static/lookup routes and reject unknown or ambiguous browser targets. |
| A09 Security Logging and Alerting Failures | Report meaningful stages and sanitized, provider-aware errors, without credentials, document content, raw provider errors, or session identifiers. Do not log viewer inputs, screenshots or Azure connection headers. The application has no centralized security alerting service. |
| A10 Mishandling of Exceptional Conditions | Bound uploads, model calls, browser operations, and active jobs. Pause preparation watchdogs during manual sign-in, resume their remaining execution budgets afterward, and retain the single-job lock throughout. The parent watchdog requests cancellation over IPC instead of killing the worker. Interrupted preparation hands an available partial form to the user with explicit warnings. Closing the browser cancels pending login; closing only the cloud viewer tab does not. Cloud expiry/restarts can end the session and lose unsaved work. Never retry uncertain human input automatically or treat an uncertain submission as confirmed acceptance. |

## Trust and residual risk

### Azure browser boundary

Hosted mode defaults to `azure`, its only supported browser mode. Extraction runs in an isolated Windows App Service worker and Chromium runs in the configured Azure Playwright workspace. An explicit retired `companion` value is rejected at startup; missing Azure configuration cannot fall back to a local browser or relay. The pairing UI, routes, relay, client and companion commands have been removed. `src/azure-browser.ts` accepts only deployment-owned canonical workspace endpoints and uses `ManagedIdentityCredential`, without developer-login or access-token fallback. The trusted server passes a connection over job-correlated private IPC; worker environment allowlists exclude managed identity settings and provider keys inherited from the server. Connection headers remain outside model context, frontend status and persistent browser storage. Remote browser network exposure is empty, so the connection does not publish App Service loopback/private networks to the workspace.

The same-origin viewer returns JPEG page images and accepts bounded mouse, text, key, scroll, popup-selection and native-dialog actions for the authenticated owner and current job. These HTTP/IPC capabilities are separate from the model tool set. Both worker status and browser phase enforce the input lock; phase transitions revoke queued input and drain in-flight operations before automation or review continues. Native dialogs can be answered by the human during login/review; pending dialogs are dismissed, never automatically accepted, when human input is suspended for preparation. Existing HTTP, WebSocket and native redirect guards continue to constrain automation. Review starts only after permanent revocation of the model's mutations.

Cloud R3 login input, including credentials and CAPTCHA responses, necessarily passes through App Service, private worker IPC and the remote browser. It is not sent to the model or stored as viewer history. The viewer clears transient typed text and queues on lock/disconnect, does not persist screenshots/input/CSRF tokens, and never retries an uncertain input request. Azure, the OS, Chromium and R3 can retain data under their own behavior and policies; in-memory application handling is not a zero-retention guarantee. No test reporter, trace or video recording is enabled by this integration.

App Service must remain a single process/instance. Sessions and browser ownership are in memory; cloud session expiry, application restart and lost remote connections may destroy unsaved work. A retired viewer cannot control a successor job. A failed successor may preserve an earlier review form under the same owner's current job, so the browser endpoint remains authoritative about availability. Closing a viewer tab does not end the cloud browser; the explicit close action does. Confirm R3 acceptance before repeating an order or submission. Synthetic viewer/guard tests do not establish live workspace connectivity, App Service identity permissions, CAPTCHA compatibility or production R3 acceptance; follow the separate [cloud acceptance sequence](azure-browser.md#synthetic-live-capability-check).

### Shared application boundary

Hosted entry navigation permits a cross-site GET only for the public `/` or `/index.html` shell, with `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document`. Host validation and any explicit Origin check still apply. API endpoints, writes, frames, embedded resources and local-mode cross-site requests retain their rejection. This follows [Fetch Metadata guidance for external navigation](https://web.dev/articles/fetch-metadata#step_3_allow_simple_top-level_navigation_and_iframing); the shell creates no session and returns no private job data. Responses remain `Cache-Control: no-store`.

The local form selects `openai`, `anthropic`, `google`, or `xai` and sends canonical `provider`, `apiKey`, and `model` fields. Blank models use `gpt-5.6-sol`, `claude-opus-5`, `gemini-3.8-flash`, or `grok-4.6`, respectively. Custom IDs have length/character validation but no model-prefix restriction or allowlist; account access and the relevant image/tool/structured-output capabilities remain necessary; the other three providers also require native PDF support. Switching providers clears the key and updates the disclosure. Custom model choices stay in page memory, separately per provider, and survive reconnection. Neither extraction nor reconciliation switches the user's provider or model after an error.

Native JSON schema output is attempted first for all four providers. Only an explicit HTTP 400 unsupported-output-format response permits a `functionCalling` format retry with the same provider, model, key, and schema; local Zod parsing always follows. Google uses the canonical nullable schema unchanged. Thinking and sampling parameters are not forced. `providerMessageMiddleware` rewrites only recognized PNG `screenshot_page` ToolMessages for OpenAI Responses and preserves the original history. Anthropic and Google accept the standard text/image blocks; Google's tool-call IDs and thought signatures remain in message history. These adaptations do not change browser tools or the human submission boundary.

`src/google.ts` constructs `@langchain/google` 0.2.5 `ChatGoogle` with `platformType: 'gai'` and a custom API-key-only `apiClient`. The SDK's default client can discover Cloud credentials even with an explicit API key, so it is bypassed. This transport pins `https://generativelanguage.googleapis.com` and `v1beta`, encodes the selected model as path data, supplies only the selected `x-goog-api-key`, rejects redirects, and combines caller cancellation with a 120-second request timeout. No Vertex/ADC/gateway discovery is used. Existing worker/browser environment allowlists are unchanged; tests explicitly exclude Google keys, Cloud credentials, project/Vertex/endpoint settings, and proxies.

Google `RequestError` uses numeric `statusCode` and private `data.error` details and may retain a key-bearing URL. The application returns fixed sanitized messages for recognized key/auth, billing/quota, model access/capability, PDF/size, schema, timeout, and blocked/invalid-output failures; unknown 400/422 rejections stay neutral. Raw SDK errors, URLs, keys, and document text are never forwarded.

Anthropic's outbound extraction schema is derived from the canonical schema: its 37 nullable text fields become required strings using empty string for unknown, while the three nullable numeric fields remain unchanged. Only those designated text paths normalize empty strings back to null before canonical Zod validation; this is not general coercion of arbitrary output. The union count drops from 40 to 3 against [Anthropic's documented maximum of 16](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#schema-complexity-limits), retaining a single native structured-output request and the selected provider/model. OpenAI's schema remains unchanged. Recognized 400/422 credit/billing, schema, PDF, and capability errors receive specific sanitized messages; unknown rejections remain neutral rather than blaming model capabilities. Raw provider errors and credentials are not exposed.

The model sees document content and relevant order-form observations. It does not receive login or CAPTCHA-page observations. Prompt-injection defenses reduce exposure but do not establish that an LLM's extracted facts are correct. Deterministic checks and the human review step remain necessary. Manual sign-in permits the user to authenticate; subsequent automated preparation rejects network writes and allows only inspected dynamic read routes. R3 changes can therefore interrupt preparation; investigate the changed behavior before widening the allowlist.

The deterministic fill pass runs before optional model reconciliation and uses the immutable approved plan. The supported URLA program controls R3 Loan Type, and Property Type uses conservative aliases for inspected options. Missing or ambiguous options remain unresolved; a free-form loan description or a missing product does not authorize guessing a dropdown value. Required facts absent from the source are tracked separately from writable plan entries, so their omission cannot produce a false claim of complete preparation.

Contact extraction requests field-specific source evidence and explicit agent-role evidence. Borrower facts primarily come from the URLA; contract details may supplement only a clearly identified same person. Agent roles primarily follow the contract's representation statements, with URLA supplementation only when identity and role are clear. Buyer/selling agents, listing agents, sellers, borrowers, and brokerages must not be substituted for one another. Purchase access uses the listing agent; refinance access explicitly fills and verifies borrower details, enables borrower access after borrower verification, then fills and verifies the access fields. Required borrower/access contacts need first and last names and at least one supported phone or email; missing details cause review rather than invention.

Missing required borrower/access names produce explicit blank plan values while retaining missing-source metadata, clearing stale identities without claiming completeness. When refinance borrower access is already checked but copied contact values are stale, the session may dispatch only that same approved native checkbox's change event after fresh borrower verification. It does not toggle the checkbox off, expose arbitrary event tools, or refresh already correct copied values.

The September 14 live contact inspection established generated `OrderItemEdit_Contacts_<UUID>__<attribute>` IDs with matching `OrderItemEdit.Contacts[<UUID>].<attribute>` names and direct Bootstrap `input-group-text` captions. The seven supported contact roles require exact nearest headings/captions, native text/email/tel inputs, matching UUID/suffix in both ID and name, one eligible identity across the entire role, and a pinned identity after its first approved action. Malformed Contacts IDs/names cannot fall back to the older agent resolver. Hidden status alternatives are excluded; multiple visible identities, split fields across identities and later identity changes fail verification. Label fallback requires one sibling caption and one form input, preventing ambiguous group labels. Historical exact IDs remain supported, and the legacy agent/officer resolver still excludes reserved IDs.

Current hidden access contacts are eligible only after fresh borrower verification with the approved borrower-copy setting true and its inspected checkbox checked. This supports readback of correct copies without forced hidden writes. Already-correct copies remain untouched; stale copies may receive the existing single guarded refresh. An unchanged borrower-field retry preserves verified copy eligibility, while an actual borrower mutation invalidates it. Contact fields remain limited to first/last name, work/home/mobile phone and email; the loan officer remains limited to first/last name, work phone and email. No address mapping, arbitrary click/evaluation tool, provider change or submission permission was added. Separate agent sections still require source facts for that role. The diagnostic retains static field metadata and keyed verification results, never credentials, document values, request bodies or contact values.

Phone recovery is limited to exactly 19 existing mapped and approved phone keys: work/home/mobile keys for `borrower`, `coBorrower`, `contact`, `listingAgent`, `buyerAgent`, and `statusContact`, plus `loanOfficer.workPhone` only. After ordinary fill/blur verification fails, it may try equivalent hyphenated and then two parenthesized US formats, skipping a candidate identical to the original plan value, then privately type the same approved number's ten US digits. Accept common formatting and an optional `1`/`+1` country prefix; never truncate extensions or international numbers to force recovery. Every mutation requires fresh same-field identity, approved mapping, editability, and active-preparation checks. Actual live masks were unavailable for inspection, so synthetic fixtures cannot establish the reported failure's exact cause or live compatibility.

Complete handoff requires fresh verification. A separate incomplete handoff permits the human to finish a partial form after preparation fails or times out. It revokes new and queued browser tools and drains in-flight actions before enabling human writes. Job status explicitly requests review and completion and retains unresolved-field warnings. Neither handoff submits an order or confirms its acceptance. Browser survival depends on keeping the responsible local development server or App Service process and browser connection running.

Sequential preparations remain restricted to the same session owner and one active preparation in every mode. The worker signals next-order readiness only after per-job cleanup, including draining old PowerShell environment operations. Each successor has a fresh controller, model, environment and approved plan. Correlated IPC and captured frontend request generations prevent retired status updates, cancellation messages, polling errors or lost-response recovery from being mistaken for the new job. Other owners cannot reuse an authenticated browser.

An explicit next-order action allows replacing the previous R3 form after new-document validation. Browser reuse retains only the existing in-memory browser session; it does not export cookies or save authentication state. Old tools remain permanently revoked. Transfer shuts down review WebSockets, drains automation, removes old handlers, and installs a fresh session on a blank page before reconfirming authentication. Submission remains human-only. Closing all browser pages releases ownership and closes production browser resources; a lingering worker cannot hold the next job hostage. This change was reviewed against the existing OWASP access-control, authentication, integrity and exceptional-condition boundaries. Live R3 acceptance is separate from the synthetic lifecycle tests.

The sequential-order review identified and corrected two additional lifetime races: helper errors must remain pending until process close and must suppress late environment synchronization; IPC sends must handle disconnect errors without discarding an existing review form. Final `npm run check` passed TypeScript checking, 336 unit/integration tests, 122 browser tests and the build (458 tests). Tests include old callbacks, owner isolation, actual second fixture submissions, environment error/closure draining, retained/expired synthetic authentication, old-tool revocation, socket retirement and owned Chromium shutdown. No live R3 order submission or paid-model call was made. The user-facing npm server was left stopped.

Appraisal Product has three paths. An explicit request needs nonempty `product` evidence naming a supplied document. An agent recommendation uses `productRecommendation` evidence in the existing evidence array and must select an inspected baseline matching the authoritative loan program. The server checks this marker first, requires nonempty source quotes, rejects mixed explicit/recommendation evidence, and rejects an explicit incompatible or unsupported property description. It adds a mandatory warning to confirm property classification and lender requirements. An uncited nonblank product remains unresolved. With no product supplied, the existing server baseline still uses the four inspected Conventional/FHA property families. These checks validate evidence structure and source-document availability, not the truth of every quoted fact; human review remains necessary.

Recommendations may consider combined one-unit/site-built facts and absence of contrary project/structure information without asserting Single Family as an extracted fact. FHA status or unit count alone is insufficient. Property Type and Occupancy normalizers remain unchanged, as do extraction fields and union counts; only the product schema description and shared instructions change. Finite optional-dash aliases for FHA SFR, Manuf, and Multi labels pass through immutable `plan.allowedLabels`; no fuzzy matching or arbitrary alternate product is permitted. This is not an underwriting or product-eligibility determination.

PowerShell Process environment changes cannot update the parent Node worker. Setters for the selected key and local loan settings therefore capture the fixed allowlisted script's result privately and explicitly synchronize the isolated worker environment. The generic `APPRAISAL_AI_API_KEY` replaces `OPENAI_API_KEY`; model-facing secret getters report availability only. Worker/browser environment allowlists reject inherited OpenAI/Anthropic keys, proxies, tracing credentials, and preload hooks. Getters inherit the job's allowlisted values in their PowerShell child. R3 usernames and passwords have no setters or getters. User and Machine variables would persist beyond the job and are not used. The scoping behavior follows [Microsoft Learn](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.6). Environment variables are not a vault and do not protect against a compromised Windows account or process inspection by privileged software.

Clearing the preparation environment also revokes its helpers. A helper that was already running cannot restore a cleared process value when it completes; late results are rejected and any restored allowlisted value is removed.

PDFs are sent inline from memory: OpenAI `input_file` blocks, Anthropic `document.source` blocks, or Google standard base64 file blocks converted to native `inlineData`. Each Google file is immediately preceded by a `Source document: urla.pdf` or `sales-contract.pdf` text label because `inlineData` has no filename. The app does not upload documents to any Files API. The 15 MiB local per-file limit is unchanged and does not guarantee provider acceptance: [Anthropic's 32 MB request limit](https://platform.claude.com/docs/en/build-with-claude/pdf-support) includes base64 expansion, all PDFs, and other request content; [Google's file-input limits](https://ai.google.dev/gemini-api/docs/generate-content/file-input-methods) and model context/page limits also apply. Oversize/capability errors are reported without exposing raw provider responses.

In-memory uploads avoid application-managed document files, but do not guarantee zero copies in OS memory, swap, crash reports, temporary browser data, or provider systems. Tracing is suppressed. OpenAI requests use `store: false`; Anthropic and Google requests do not receive unsupported storage flags. Provider retention terms and account settings still apply; no integration promises zero retention. [OpenAI's data controls](https://developers.openai.com/api/docs/guides/your-data) describe its provider-side behavior. Normal R3 session and order retention are controlled by R3.

## SpaceXAI / Grok change

`src/xai.ts` uses LangChain `ChatXAI` and a fixed xAI Chat Completions endpoint. Explicit credentials, filtered outbound headers, redirect rejection, cancellation, and a 120-second per-request timeout preserve job isolation. Ambient xAI/Grok credentials, endpoints, proxies and tracing are excluded by the existing worker/browser allowlists. No search or other provider-hosted tools are enabled. Errors are classified into fixed safe messages; unknown rejections remain neutral.

Grok documents are rendered locally in memory through PDF.js and native canvas, without public URLs or Files API uploads. Every page is labeled by source and page number. Only fixed installed font/CMap/wasm assets may be read; resource-name validation prevents paths or URLs escaping those directories. PDF scripts are not executed. Preflight caps input at 50 total pages, each PNG at 20 MiB, total output at 40 MiB PNG bytes, and conversion at a 60-second cooperative budget; pages are sized to at most 2400 pixels per edge. Native encoding and cleanup are awaited; a single native operation may finish after cancellation before cleanup completes. Rendering errors or limits prevent model extraction rather than silently omitting pages. PDF parsing/decoding adds local CPU/memory and native dependency exposure; these bounds are not a proof that every malformed PDF is harmless.

The canonical schema and loan rules are unchanged. Grok screenshots move only from recognized PNG screenshot tool results to a following image-bearing user message, after all contiguous tool results. Original tool IDs/history and the immutable browser plan remain intact. The manual submission and browser lifetime boundaries are unchanged.

`npm run check` passed with exit code 0: TypeScript checking, 314 unit/integration tests across 14 files, 66 Playwright tests, and the production build (380 tests total). Installation of `@langchain/xai` 1.4.12, PDF.js, and native canvas reported zero known dependency vulnerabilities. Live Grok and live R3 behavior remain unverified.
