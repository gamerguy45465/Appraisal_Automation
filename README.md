# Appraisal Automation

A Windows desktop workflow that reads a URLA and optional sales contract, then prepares an R3 AMC appraisal order in a visible Chromium window. The application stops at human review. Only the user submits the appraisal order.

The application uses an HTML/CSS/JavaScript frontend, Express and TypeScript, LangChain for JavaScript, OpenAI Responses, Anthropic Messages, Google Gemini, or SpaceXAI (Grok), and Playwright's TypeScript API. Select a provider and enter a model ID, or leave it blank to use that provider's default. The application never switches providers or models automatically.

| Provider | Default model when blank |
| --- | --- |
| OpenAI (initial selection) | `gpt-5.6-sol` |
| Anthropic | `claude-opus-5` |
| Google Gemini | `gemini-3.8-flash` |
| SpaceXAI | `grok-4.6` |

## Business rules

- URLA loans identified as VA are rejected with instructions to use the VA portal.
- FHA and FHA Zero Down loans require the separately entered FHA case number.
- The supported URLA loan-program classification sets R3 Loan Type: Conventional or FHA, including FHA Zero Down. Free-form rate or loan-type text cannot override that classification. Property Type uses explicit, conservative aliases for inspected R3 options; unsupported descriptions remain unresolved for review.
- Branch is `GUILD 685 SUMMERLIN ONE`.
- Sale price is populated only for a purchase with a supplied sales contract. Extract the explicit purchase/sale price from its filled fields, exhibits, and addenda even if it is unsigned, a draft, or a sample; retain a status warning for review. Request contract-page/quote evidence, keep the positive amount separate from financing and valuation figures, and use null with a review warning for missing or unresolved prices, never zero. Refinances and orders without a contract leave sale price blank.
- Purchase access contact uses the listing agent when supported by the documents, with borrower access unchecked. Refinance access contact uses the borrower's details explicitly: fill and verify the borrower, enable borrower access, then fill and verify the access fields instead of relying only on R3's checkbox behavior.
- Borrower and required access contacts need first and last names plus at least one supported phone number or email. Preserve documented phone types; unavailable or ambiguous contact details require review and must not be invented.
- Missing required borrower/access names explicitly clear any stale field values and remain flagged as missing. If refinance borrower access is already checked but its copied contact is stale, preparation refreshes that same checked control after verifying the borrower; correct copied values are left alone.
- Listing agent and seller's agent mean the same seller-representative role; Buyer's Agent is separate. Extraction requests evidence for each contact field and the represented party, using the contract's explicit agent information and supplementing from the URLA only when identity and role are clear. Classify a selling/cooperating agent as `buyerAgent` only when the document explicitly establishes buyer representation; do not confuse "selling agent" with "seller's agent." Populate each separate agent section when any source fact for that role is known.
- Status contact is `Amber Coleman Team`, email `ambercolemanteam@guildmortgage.net`.
- Always fill the loan officer's first name `Amber`, last name `Coleman`, work phone `702-604-7027`, and email `acoleman@guildmortgage.net`. These required values are fixed in the approved plan for every order, independent of document contents, provider, or loan purpose. The separate status contact stays unchanged.
- If an existing mapped phone field does not retain its approved value after filling and leaving the field, preparation may retry equivalent US formats, then use private guarded digit entry. Each field keeps its own approved number; blank values stay blank. Final verification must confirm that same number, or require review.
- APN, agency case IDs, lockbox, access instructions, inspection preference, and special handling stay blank; county remains Unknown and Side-by-Side stays unchecked.
- Product means the appraisal service/form, not mortgage financing. A stated appraisal request needs a document citation. Otherwise, the agent may recommend an inspected baseline product from combined document facts, citing those facts separately and warning that property classification and lender requirements need confirmation. A recommendation does not establish Property Type or Occupancy and cannot override an explicit incompatible or unsupported property description.
- When no product is supplied, the existing server baseline uses the inspected property/program pairs below. Missing evidence, conflicting facts, mixed explicit/recommendation citations, or an unsupported recommendation leave Product unresolved for review.
- Missing borrower, contact, loan-purpose, and property facts remain unknown or are reported for review. The model must not invent them.

The server baseline uses documented property type and loan program; the recommendation path uses the same inspected product families and must match the loan program. FHA Zero Down uses the FHA column. Neither path establishes lender-specific eligibility or additional appraisal requirements. A one-unit, site-built residence without contrary condominium/manufactured/multi-unit facts may support a tentative single-family product recommendation; FHA status, unit count, occupancy, price, or loan amount alone is insufficient. Property Type and Occupancy remain independently extracted.

## Architecture and data lifetime

The local server validates the form and PDF upload, authenticates requests with an in-memory session and CSRF protection, and permits one active preparation. An isolated Node worker may retain the same owner's R3 browser between orders. Each order gets a fresh cancellation controller, model, environment and guarded session; IPC messages carry its job ID. Each environment setter passes a literal value through standard input to the fixed `scripts/environment.ps1` script, which sets and retrieves an allowlisted **Process** variable. The worker privately captures the result and explicitly synchronizes its own environment; getter tools call the script with the worker's environment. Values are not interpolated into executable PowerShell commands. Cleanup drains any old environment operations before the next order can begin.

Process scope is intentional: the selected API key uses the generic `APPRAISAL_AI_API_KEY` worker variable, with local loan settings, without being saved to the Windows User or Machine registry scopes. Canonical form fields are `provider`, `apiKey`, and `model`; `apiKey` replaces `openaiApiKey`. Worker and browser environment allowlists exclude inherited provider keys and proxies. R3 sign-in stays in the browser session. A child PowerShell process cannot update its parent Node environment, so the worker synchronizes explicitly. This behavior follows [Microsoft's environment variable documentation](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.6).

The worker delegates to `runPreparation` in `src/preparation.ts`, which extracts structured facts from the PDFs, applies deterministic business validation, waits for manual R3 sign-in, and prepares the form at `https://clients.r3amc.com/Orders/Create`. A deterministic pass fills and verifies the approved plan before optional model reconciliation of unresolved fields. No agent observations or form actions run on the login/CAPTCHA page. Tool access ends at handoff. The API key, documents, and job state are held in memory rather than application-created persistent storage. Runtime memory, OS paging or crash dumps, and R3/Chromium's temporary session files are outside any claim of secure erasure.

Both preparation watchdogs retain their processing budgets and pause during manual sign-in. The parent watchdog requests `stop_preparation` over worker IPC instead of killing the browser-owning worker. Incomplete handoff revokes new and queued tool actions and drains in-flight actions before enabling human writes. Complete handoff still requires fresh field verification. After cleanup acknowledges readiness, the same owner may explicitly begin the next order. Old tools remain revoked; a new preparation installs fresh guards and rechecks authentication. Closing the final browser page releases the lock without waiting indefinitely for its worker process to exit.

Historical exact field IDs remain supported. The September 14 contact inspection established the current `OrderItemEdit_Contacts_<UUID>__<attribute>` IDs and matching `OrderItemEdit.Contacts[<UUID>].<attribute>` names. Because UUIDs change between forms, the seven supported roles require exact section headings, exact field captions, matching ID/name/suffix, one eligible identity across the role, and identity revalidation before writes and at final review. New `input-group-text` labels require one sibling caption and one input in the group. Other fields retain their existing mapping, and the legacy agent/officer caption resolver excludes reserved IDs and the current Contacts namespace. Contact fields remain limited to names, work/home/mobile phone and email; loan-officer fields remain only first/last name, work phone and email. No contact-address or additional loan-officer mappings were added.

Phone recovery covers exactly 19 existing mapped phone keys: work/home/mobile fields for borrower, co-borrower, access contact, listing agent, buyer agent, and status contact, plus loan-officer work phone only. It adds no planned values or mappings and never substitutes the officer's number for another contact. The conservative `phoneInputDigits` helper accepts ten US digits with common formatting and an optional `1`/`+1` country prefix. Recovery tries equivalent hyphenated `702-604-7027` and then parenthesized `(702)604-7027` / `(702) 604-7027` formats, skipping a candidate identical to the original plan value because the initial fill already tried it. It does not truncate extensions or international numbers into a different US number. Each mutation freshly checks field identity, mapping, editability, and active preparation. Refinance still verifies the borrower before the protected access-contact copy. No model keyboard tool or submission action is added.

Each client receives the selected key explicitly and uses a pinned official endpoint: `https://api.openai.com/v1`, `https://api.anthropic.com`, `https://generativelanguage.googleapis.com`, or `https://api.x.ai/v1`. OpenAI, Anthropic, and Google PDFs stay in memory and are sent inline as provider-native base64 blocks (`input_file`, `document.source`, or standard base64 file blocks converted to `inlineData`, respectively), without Files API uploads. Google files have preceding source-document text labels. Grok receives locally rendered page images as described below. OpenAI Responses requests set `store: false`; other providers receive no unsupported `store` flag. No integration promises zero provider retention; provider terms and account settings apply. See [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).

Google uses `@langchain/google` 0.2.5 `ChatGoogle` through `src/google.ts`, with `platformType: 'gai'` and an API-key-only `apiClient`. This bypasses the SDK's ambient Cloud credential discovery, even when unrelated credentials are present. Requests use the pinned `v1beta` Generate Content endpoint, an encoded model path, no redirects, and both caller cancellation and a 120-second request timeout. Existing worker/browser environment allowlists remain unchanged and exclude Google keys, ADC/Vertex credentials, project/endpoint settings, and proxies.

Grok uses `@langchain/xai` 1.4.12 `ChatXAI` through `src/xai.ts`. Its public `clientConfig` is set after construction because the adapter replaces constructor configuration. The isolated transport permits only POST to `https://api.x.ai/v1/chat/completions`, sends the selected bearer key, rejects redirects, removes ambient organization/project headers, and combines caller cancellation with a 120-second request timeout. It enables no search tools. Existing worker/browser allowlists also exclude inherited `XAI_API_KEY`, `GROK_API_KEY`, endpoint, and tracing settings.

[xAI's documented file attachment paths](https://docs.x.ai/developers/model-capabilities/files/chat-with-files) use uploaded file IDs or public URLs. This application instead uses `src/pdf-pages.ts` with `pdfjs-dist` 6.3.289 and `@napi-rs/canvas` to render all pages in memory, without Files API uploads or public document URLs. Each PNG has a source-document and page-number marker. Rendering targets 144 DPI with a 2,400-pixel longest-side cap, applies the limits above, and rejects unreadable/password-protected PDFs or dynamic XFA forms requiring flattening. No partial set of pages is sent. Other providers retain native PDF handling.

## Model and integration status

Defaults are OpenAI [`gpt-5.6-sol`](https://developers.openai.com/api/docs/models/gpt-5.6-sol), Anthropic [`claude-opus-5`](https://platform.claude.com/docs/en/models/opus-5/overview), Google `gemini-3.8-flash`, and SpaceXAI `grok-4.6`. The application uses LangChain's [ChatOpenAI](https://docs.langchain.com/oss/javascript/integrations/chat/openai), [ChatAnthropic](https://docs.langchain.com/oss/javascript/integrations/chat/anthropic), [ChatGoogle](https://docs.langchain.com/oss/javascript/integrations/chat/google), and [ChatXAI](https://docs.langchain.com/oss/javascript/integrations/chat/xai) integrations without forcing thinking or sampling parameters.

Extraction first requests native JSON schema output. For Anthropic, the outbound schema represents 37 nullable text fields as required strings, with an empty string meaning unknown; only those text paths are restored to canonical null before local Zod validation. The three nullable numeric fields remain numeric/null, and the OpenAI schema is unchanged. This reduces the outbound union count from 40 to 3, within [Anthropic's documented limit of 16](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#schema-complexity-limits). It retains a single native structured-output request with the selected provider/model and does not force thinking settings.

Only an explicit HTTP 400 rejection of the native output format permits a retry using `functionCalling` with the same provider, model, key, and outbound schema; local Zod parsing always validates the result. Google and Grok use the unchanged canonical nullable schema. Sanitized provider errors distinguish recognized key/access, billing/quota, schema, size, and capability problems; an unclassified 400/422 does not assume the model lacks capabilities. Google SDK `statusCode` and xAI's OpenAI-compatible nested errors are inspected without forwarding raw messages, URLs, or keys. The optional reconciliation agent uses that same model and unchanged browser permissions. Browser screenshots use standard text/image blocks; `providerMessageMiddleware` converts recognized PNG `screenshot_page` tool messages to OpenAI Responses blocks or, for Grok, retains the text tool response and adds its images in a user message after the contiguous tool-response group. Anthropic and Google accept standard blocks. Existing tool-call IDs and Google thought signatures stay with the original message history.

The authenticated R3 create-order page and its inline scripts were inspected read-only during development, including field names and dependent lookup routes. No real order fields were filled or submitted as part of that inspection. Account-level access to the selected provider/model, extraction quality on real mortgage documents, and the complete runtime manual-login/fill/handoff sequence still require an authorized acceptance run. Automated fixture tests and request-serialization tests do not establish live integration success. If a label is missing, ambiguous, or incompatible, the automation should stop or report the unresolved field rather than force a value.

The implementation should therefore be treated as locally verified software awaiting live integration acceptance, not a certified production deployment. No real appraisal has been submitted during development. Manual sign-in is user controlled. After authentication, preparation-time network writes are denied and dynamic reads are limited to inspected R3 lookup routes. Changed or additional R3 endpoints need investigation before being added to that allowlist.
